# Theme Authoring Pitfalls and Verification Notes

This note captures regressions encountered while adding the Hermes theme so future theme work avoids the same traps.

## 1. `MudTabs` can stay transparent even when `ApplyEffectsToContainer="true"`

### What happens

When `MudTabs` uses `ApplyEffectsToContainer="true"`, MudBlazor moves the rounded, outlined, and elevation classes onto the root `.mud-tabs` element instead of the tab bar.

That means a theme can accidentally style cards, papers, and drawers correctly while leaving:

- `.mud-tabs` transparent
- `.mud-tabs-panels` transparent
- the tab shell visually broken on pages such as dashboards or tabbed tools

### What to inspect

- Root `.mud-tabs`
- Direct child `.mud-tabs-tabbar`
- Direct child `.mud-tabs-panels`
- MudBlazor source:
  - `Components/Tabs/MudTabs.razor.cs`
  - `Styles/components/_tabs.scss`

### Preferred fix

Use shared theme selectors against the MudBlazor structure, for example the root container shapes generated by `mud-tabs-rounded`, `mud-paper-outlined`, or `mud-elevation-*`.

Do not fix this by adding page-only hooks such as `dashboard-tabs` or `project-units-tabs` unless the page genuinely owns a unique layout.

## 2. `MudDataGrid` header controls are intentionally hover-hidden by default

### What happens

MudBlazor hides several header affordances until hover. In some themes this makes the header look blank or broken.

Relevant elements include:

- `.sort-direction-icon`
- `.column-options-icon`
- `.drag-icon-options`
- `.column-options .mud-menu .mud-icon-button-label`

### What to inspect

- Live header DOM on the target page
- Computed `opacity` and `color`
- MudBlazor source:
  - `Styles/components/_datagrid.scss`

### Preferred fix

If the theme needs persistent affordances, define a visible default state with muted color and a stronger hover state.

Do this at the theme level for shared `MudDataGrid` structure, not with page-local selectors.

## 3. Manual theme verification must use the real storage key

In Monica UI, `IBrowserStorage` automatically prefixes keys with `mo:`.

Application code uses:

```csharp
await BrowserStorage.GetAsync<ThemeData?>("theme:data", null);
```

The actual browser `localStorage` key becomes:

```text
mo:theme:data
```

### Rule

- In application code, pass `theme:data` to `IBrowserStorage`
- In Playwright, DevTools, or raw `localStorage` debugging, write `mo:theme:data`

If you write only `theme:data` during manual verification, the theme will appear to ignore persisted state.

## 4. Screenshot-only debugging is not enough

Theme regressions should be diagnosed from:

- live DOM
- computed styles
- emitted selectors
- MudBlazor source when behavior is uncertain

Screenshots are confirmation artifacts, not the primary diagnostic tool.

## 5. Verify shared components on more than one page

A theme fix that works on one page can still miss reused MudBlazor structures elsewhere.

Minimum verification for a new theme:

1. Check both light and dark modes.
2. Check at least two routes that reuse the same MudBlazor component type.
3. Re-verify after removing any temporary page-specific hooks added during diagnosis.
